# 核心逻辑
## 客户端连接的关闭：
## 1，一定由客户端发起，【不再产生新的请求，是关键起点】。
## 2，客户端【确认】提交给服务端处理的所有任务，都已经完成时，是关键终点，由【客户端】主动关闭连接。
## 3，服务端关机时，只是重复“关闭客户端”，直到所有客户端都安全关闭后，才关闭自身。

## 客户端开始连接 -> ♻服务进行♻ -> 客户端处理完所有提交的任务，客户端发起关闭。

#客户端发起的【客户端关机】操作

1. 标记当前客户端为【关机中状态】。
2. 异步等待:所有【Socket连接】关闭，从而使得客户端成为【可关机的状态】。
3. 新的Api请求，直接拒绝放入【待发送队列】，返回信息：处理失败。
4. 客户端，继续：发送完【待发送任务队列】。
5. 客户端，继续：接收【待接收任务队列】。
6. 当客户端中最后一个【待处理的业务请求】被完整处理完后（DidResponseProcessEnd）：
	由于当前处于【关机中状态】，因此，**此时向服务端调用【客户端断开连接Api】：**
    * 此时【客户端】和【服务端】之间已不存在需要处理的【业务请求、业务响应】，仍然会接收来自服务端发起的请求，如：【心跳请求】。
    * 此时**【客户端】不再发送任何请求到【服务端】**，一直等待来自服务端的【客户端关闭连接Api】响应。
    * 服务端接收到【客户端关闭连接Api】的调用后，不再向客户端发送【心跳请求】，同时标记当前【客户端连接】为【关机中状态】，**【服务端不再使用该连接向客户端传输数据】**。
7. **客户端收到来服务端的【客户端关闭连接Api】响应后，可以确定服务端已将此连接标记为可关机状态**，此时，客户端，服务端，都已经不再使用当前【客户端连接】，因此，客户端可以安全的关闭【Socket连接】。

#服务端发起的【服务端关机】操作

1. 标记当前服务端为【关机中状态】。
2. 异步等待所有【客户端连接】关闭，从而使得服务端成为【可关机的状态】。
3. 向所有已连接的【客户端】，广播【服务端关机】命令，客户端收到该命令后，则发起【【客户端关机】操作】。
3. 新的客户端新建连接，都会被拒绝。
4. 所有已连接的客户端，都会开始【【客户端关机】操作】。
5. ...所有客户端执行【客户端发起的【客户端关机】操作】...
6. **所有客户端关闭连接后，服务端安全结束服务。**


#客户端发起的【服务端关机】操作
1. 客户端向服务端发起【服务端关机命令】。
2. 服务端开始执行**【服务端发起的【服务端关机】操作】**流程。
3. ...服务端执行【服务端发起的【服务端关机】操作】...
4. 所有客户端关闭连接，安全关机。
5. 服务端关闭所有客户端连接，安全关机。
